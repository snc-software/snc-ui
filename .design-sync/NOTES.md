# design-sync notes — @snc-software/snc-ui

## [GENERAL] fixes already applied (don't re-diagnose these)

- **`.storybook/preview.ts` decorator never bundles** — `withColorScheme` decorator imports `../src/index.css`, which pulls in Tailwind's `@import "tailwindcss"`; plain esbuild can't resolve that without the Vite/PostCSS pipeline. Build prints `! preview decorator bundle failed: Could not resolve "tailwindcss"` on every run — expected, non-blocking. Effect: previews render WITHOUT the decorator's padded/bordered/background wrapper div that Storybook shows. Per the compare rubric this is framing chrome ("judge the component, not its surroundings") — do not mark stories `mismatch` for missing the white bordered card around the component; judge the component itself.
- **`cfg.tsconfig` comment-stripper bug** — the shared `tsconfigPathsPlugin` (bundle.mjs) strips `/* ... */` comments with a regex that also matches the literal `/*` inside a wildcard path key like `"@/Components/*"`, corrupting the JSON and silently returning a null plugin (no error). Worked around with a dedicated `.design-sync/paths-tsconfig.json` that expresses wildcard paths without a `/` directly before the `*` (e.g. `"@/Components*": ["./src/Components*"]`), which resolves identically via prefix-matching but avoids the literal `/*` substring. `cfg.tsconfig` points at this file, not the repo's real `tsconfig.app.json`. Also has an explicit exact-match entry for `@/Components/Typography` → `./src/Components/Typography/index.ts` because the plugin's ext-search checks the bare directory (`existsSync` true) before `/index.ts`, and `Typography` isn't shimmed to the bundle global (it's a barrel, not itself an exported component name), so it tried to load the directory as a file.
- **`cfg.cssEntry`** — `dist/snc-ui.css` (Tailwind output) references `var(--snc-*)` tokens that are defined in the SEPARATE `dist/design-tokens.css`, not inline. `cfg.cssEntry` only accepts one file, so `buildCmd` concatenates both into `.design-sync/combined-styles.css` after every `npm run build`, and `cssEntry` points at that.
- **[GENERAL] Shipped-bundle bug, fixed in `vite.config.ts`** — `zustand` → `use-sync-external-store`'s CJS shim does a plain top-level `require("react")`. Because it's inside a lazily-evaluated CJS-interop wrapper, Rollup can't hoist it to the externalized `react` import and instead leaves a runtime `require()` call, which throws `Dynamic require of "react" is not supported` in ANY plain-browser environment with no global `require` — this crashed the ENTIRE `_ds_bundle.js` at load (before any component was defined), not just Sidebar/table components, because merely importing `zustand` anywhere triggers it eagerly. This is a real defect independent of design-sync — it would break any consumer loading this package without a bundler smart enough to re-interop it (and DOES break Claude Design's runtime, which loads bundles as a plain global script). Fixed with a `fixCjsReactRequire()` Vite plugin (`enforce: 'pre'` transform) that rewrites that one `require("react")` call to a real `import __React from 'react'` before Rollup's CJS interop sees it, for any file matching `use-sync-external-store` in its id. Verified: 0 occurrences of the broken pattern post-fix, all 1162 existing tests still pass, all 40 components resolve on `window.SncSoftwareSncUi`.
- **`Sidebar` — duplicate React Context** — `Sidebar.stories.tsx` imports `useSidebar` via a relative path (`from './Sidebar.context'`), which isn't recognized by the story-import shimming policy as belonging to the `Sidebar` component family (the file name `Sidebar.context` doesn't match an exported component name), so it got bundled fresh from source instead of shimmed to the compiled bundle global. That created a second, distinct `SidebarContext` object — `SidebarProvider` (from the real bundle) provides one instance, the story's `useSidebar` read a different one — so every sub-component threw "must be used within a SidebarProvider". Fixed via `cfg.storyImports.shim: ["Sidebar.context"]`.
- **`cfg.overrides` cardMode fixes applied**: `BarChart`, `LineChart`, `MasterDetailsTable`, `NavigationBar`, `PieChart`, `Table` → `cardMode: "column"` (stories render wider than a grid cell). `CmdK` → `cardMode: "single", primaryStory: "Default"` (portal/fixed-position content escapes the grid).

## Known non-blocking warnings

- `Spinner`, `ThemeToggle`, `IconButton` — `[RENDER_THIN]` (variants look similar / mounts paint minimal content). Verified visually via compare — all three are small icon-only components with genuinely little visual variation between story variants; not a bug.
- `[FONT_REMOTE]` "Manrope", "JetBrains Mono" — fonts load via Google Fonts CDN `@import` in `styles.css` (no local font files in this repo). Confirmed rendering correctly via the `Heading` compare (JetBrains Mono renders identically on both sides).

## Re-sync risks

- The `fixCjsReactRequire` plugin pattern-matches on `id.includes('use-sync-external-store')` and the literal `require("react")` text — if `use-sync-external-store` (or zustand's dependency on it) changes its internal source structure in a future version, re-verify this still catches it (check `dist/snc-ui.es.js` for `I("react")`-style dynamic-require wrappers after any `npm update`).
- `Modal`'s stories don't force the modal into an open state, so only the closed-state trigger button is verified — the actual modal content/overlay has never been visually compared against Storybook. If modal content styling changes, this won't be caught until an owned preview forces `isOpen`.
- The decorator-bundle failure (tailwindcss unresolvable) means NO story-level theme decorators apply to previews, including dark-mode toggling via `context.globals.theme` — all previews render in light mode regardless of what a story's globals would set in real Storybook. Fine today since `initialGlobals.theme` defaults to `'light'` and no story overrides it per-story, but flag if a future story starts relying on the dark decorator.
- **`BarChart`/`LineChart` — `[PORTAL?]` on the product card, verified benign.** Recharts mounts an always-present, absolutely-positioned tooltip/cursor wrapper for Cartesian charts (Bar/Line — Pie doesn't have this), which validate's structural heuristic flags as overlay content that could escape its grid cell in the full multi-story product card. No story ever opens/hovers it, and all per-story isolated captures pixel-match storybook exactly, so this is very likely a non-issue in practice (the wrapper has no visible content until hover). Did not change `cardMode` — `column` (already applied for a separate width `[GRID_OVERFLOW]` issue) keeps all 4 stories visible in the product card, whereas the suggested `single` fix would only show one story. If this ever turns out to visibly bleed in the live product view, revisit.
- `SearchInput` (11 stories), `Select` (9), `MultiSelect` (11) exceed the default 6-story capture cap — only the first 6 were captured/graded each. Primary story graded clean `match` and all three are warning-free, so per the §4 sampling rule this is within bounds, but the tail stories were never individually verified. Re-run with `--max-stories <n>` to cover them fully if those tail variants matter.
- `CmdK`'s "Live Search" story: storybook's own canvas screenshot crops to ~106px (sized by the story root's normal-flow bounds, which the `position:fixed` portal dialog escapes) while the preview shows the full 700px dialog. Graded match — the visible sliver is consistent with the full preview — but this means only a thin strip of that story was ever visually cross-checked against storybook.
